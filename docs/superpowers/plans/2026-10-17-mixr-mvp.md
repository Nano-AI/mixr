# mixr MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A UW student texts mixr their interests, gets a compatible 1:1 or small-group proposal with a concrete time and public place, accepts it, and receives a confirmed meetup, with no human organizer involved.

**Architecture:** One Node/TypeScript process with one SQLite file. Three modules share it: `messaging` (Messaging dev: phone ↔ app), `matching` (Matching dev: braindump → profile → vectors → candidates), `meetups` (Meetups dev: proposals, responses, scheduling, lifecycle). Modules talk only through the five interfaces in `src/types.ts`. A 60-second `tick()` drives the time-based work (expiry, reminders, feedback, retries, planning).

**Tech Stack:** Node ≥ 24 (native TS type-stripping), `node:sqlite`, `node:http`, `node:test`, Photon v2 (messaging), `@anthropic-ai/sdk` (`claude-haiku-5-5`, profile extraction), `@huggingface/transformers` (`Xenova/all-MiniLM-L6-v2`, 384-dim, local embeddings).

**Spec:** the team brief, pasted into the planning session on 2026-10-17. Overview in `PLAN.md`. The binding parts are restated below.

## Global Constraints

- Language: TypeScript run directly by Node (`node src/server.ts`). **Erasable syntax only**: no `enum`, no `namespace`, no constructor parameter properties. Import paths include the `.ts` extension.
- Runtime deps are limited to `@anthropic-ai/sdk` and `@huggingface/transformers`, plus a Photon SDK if Photon v2 ships one. Dev dep: `typescript` (for `tsc --noEmit`). Don't add any others without asking the team.
- One database: SQLite at `process.env.DB_PATH` (default `mixr.db`). Tests use `:memory:`.
- Process timezone: `TZ=America/Los_Angeles` (all slot math uses local `Date` methods).
- Voluntary opt-in only. **No student-directory scraping**: UW prohibits commercial use and it is legally risky as spam. Signup is via a shared number or QR code.
- Phone numbers are never shown to other users. Confirmations share **first names only**.
- Opt-out keywords stop all messaging immediately: `STOP`, `STOPALL`, `UNSUBSCRIBE`, `END`, `QUIT`.
- Email verification proves access to a `@uw.edu` address. It does **not** prove current enrollment, and the copy must not claim it does.
- Cosine similarity ranks candidates. It is **not** a "personality compatibility" score. Never phrase it that way to users.
- Group meetups: 3–6 people. Pair meetups: exactly 2. A meetup confirms only when `min_size` people have explicitly accepted.
- Every invitation is addressed by its meetup id (`YES 12`) so a reply can't accept the wrong proposal.
- State changes happen inside a DB transaction. Messages are sent **after** commit, never inside a transaction.
- Tunable constants live at the top of the file that uses them, each with a `// tune:` comment. No config module.

## Review Focus

1. **Bare "YES" with two open invitations.** The user must be asked which one (`Reply YES 12 or YES 15`), and nothing is accepted. Test: Task W3.
2. **Two YES replies racing for the last seat.** Exactly one is accepted, the other gets `full`, and the accepted count never exceeds `max_size`. Test: Task A2.
3. **YES after the deadline, or on an expired/cancelled meetup.** The reply is "that one closed", and neither the invitation nor the meetup changes. Test: Task A2.
4. **Photon re-delivers the same inbound webhook.** It's processed once and replied to once (inbound `provider_id` dedupe plus `reply:{providerId}` outbound dedupe key). Test: Task W2.
5. **STOP from someone holding an accepted seat.** No further messages go out, their seat is released, and the meetup is re-evaluated (backfill, or cancel if below min). Test: Task W3 (routing) and Task A2 (seat release).

```sql
CREATE TABLE IF NOT EXISTS users (
  id INTEGER PRIMARY KEY,
  phone TEXT NOT NULL UNIQUE,                       -- E.164
  name TEXT,
  email TEXT,
  email_verified INTEGER NOT NULL DEFAULT 0,
  step TEXT NOT NULL DEFAULT 'new',                 -- onboarding step (messaging/onboarding.ts)
  mode TEXT NOT NULL DEFAULT 'both' CHECK (mode IN ('pair','group','both')),
  opted_out INTEGER NOT NULL DEFAULT 0,
  reliability REAL NOT NULL DEFAULT 1200,           -- Elo (meetups/feedback.ts)
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE IF NOT EXISTS profiles (
  user_id INTEGER PRIMARY KEY REFERENCES users(id),
  braindump TEXT NOT NULL,
  data TEXT NOT NULL,                               -- JSON Profile
  confirmed INTEGER NOT NULL DEFAULT 0,
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE IF NOT EXISTS interests (               -- one vector per interest, not per braindump
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  label TEXT NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('does','wants_to_try')),
  level TEXT NOT NULL CHECK (level IN ('new','casual','experienced')),
  category TEXT NOT NULL CHECK (category IN ('sport','talk','other')),
  embedding BLOB NOT NULL                           -- Float32 x 384, L2-normalized
);
CREATE INDEX IF NOT EXISTS interests_user ON interests(user_id);
CREATE TABLE IF NOT EXISTS availability (
  user_id INTEGER NOT NULL REFERENCES users(id),
  slot TEXT NOT NULL,                               -- ISO start, from meetups/slots.ts
  PRIMARY KEY (user_id, slot)
);
CREATE TABLE IF NOT EXISTS meetups (
  id INTEGER PRIMARY KEY,                           -- also the reply code: "YES 12"
  kind TEXT NOT NULL CHECK (kind IN ('pair','group')),
  activity TEXT NOT NULL,
  category TEXT NOT NULL CHECK (category IN ('sport','talk','other')),
  place_id TEXT NOT NULL,
  slot TEXT NOT NULL,
  min_size INTEGER NOT NULL,
  max_size INTEGER NOT NULL,
  deadline TEXT NOT NULL,
  visibility TEXT NOT NULL CHECK (visibility IN ('public','private')),
  state TEXT NOT NULL DEFAULT 'proposed'
    CHECK (state IN ('proposed','confirmed','expired','cancelled','done')),
  seed_embedding BLOB NOT NULL,
  embedding BLOB NOT NULL,                          -- biased toward accepted members
  host_user_id INTEGER REFERENCES users(id),
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE IF NOT EXISTS invitations (
  meetup_id INTEGER NOT NULL REFERENCES meetups(id),
  user_id INTEGER NOT NULL REFERENCES users(id),
  state TEXT NOT NULL DEFAULT 'pending'
    CHECK (state IN ('pending','accepted','declined','cancelled','expired','full')),
  responded_at TEXT,
  PRIMARY KEY (meetup_id, user_id)
);
CREATE TABLE IF NOT EXISTS message_jobs (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  dedupe_key TEXT NOT NULL UNIQUE,
  text TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','sent','failed')),
  attempts INTEGER NOT NULL DEFAULT 0,
  error TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  sent_at TEXT
);
CREATE TABLE IF NOT EXISTS inbound_messages (
  provider_id TEXT PRIMARY KEY,
  phone TEXT NOT NULL,
  text TEXT NOT NULL,
  received_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE IF NOT EXISTS feedback (               -- row with attended NULL = request outstanding
  meetup_id INTEGER NOT NULL REFERENCES meetups(id),
  user_id INTEGER NOT NULL REFERENCES users(id),
  attended INTEGER,
  note TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (meetup_id, user_id)
);
```

### Task W3: Inbound router + keywords

**Files:** Create `src/messaging/router.ts`; Test `test/messaging/router.test.ts`

**Interfaces:**
- Consumes: `recordResponse`, `openInvitations` (A2), `recordFeedback` (A5), `listPublicEvents`, `joinEvent` (A6), `onboardingStep` (W4)
- Produces: `handleInbound(m: Inbound): Promise<void>`

Routing order (first match wins). Normalize first: trim, collapse whitespace, strip trailing `!.?`, and match keywords case-insensitively on the first word.
1. Find or create the user by `m.from`.
2. `STOP|STOPALL|UNSUBSCRIBE|END|QUIT` → `opted_out=1`, call `recordResponse(u, id, 'cancel')` for each of `openInvitations(u,'cancel')` and decline each `openInvitations(u,'yes')`, then send `"You're unsubscribed from mixr. Reply START to come back."` with key `stop-ack:{providerId}`.
3. Opted out and not `START` → do nothing (send no reply). `START` → `opted_out=0`, reply with a welcome back.
4. `HELP` → the help text: the keyword list plus "msg frequency varies, reply STOP to quit".
5. `YES|PASS|CANCEL [n]`: if `n` is given, call `recordResponse(u, n, r)`. Otherwise use `ids = openInvitations(u, r)`: if there's 1, use it; if 0, reply `"No open invites right now."`; if there are 2 or more, reply `"Which one? Reply YES 12 or YES 15"` (list the ids) and accept nothing.
6. `WENT|MISSED` → `recordFeedback(u, attended, rest-of-text)`.
7. `EVENTS` → `listPublicEvents(u)`. `JOIN n` → `joinEvent(u, n)`.
8. `EDIT` → `step='braindump'`. `FREE` → `step='availability'`. Then fall through to 9.
9. Otherwise → `onboardingStep(u, text)`.

All direct replies use the dedupe key `reply:{providerId}`. Check the Photon docs: if its SMS route treats `CANCEL` as a carrier opt-out keyword, rename the meetup keyword to `DROP`. Keep keywords in one exported `const` array per route.

### Task J3: `findCandidates`

**Files:** Replace `src/matching/candidates.ts`; Test `test/matching/candidates.test.ts`

**Interfaces:**
- Consumes: `cosine`, `fromBlob`, `Criteria`, `Candidate`
- Produces: `findCandidates(c: Criteria): Candidate[]`, sorted by `score` descending, `limit` default 20

Algorithm:
1. **Hard filters in SQL:** `opted_out=0`, `step='active'`, `profiles.confirmed=1`, `mode IN (c.kind, 'both')`, `id NOT IN excludeUserIds`. If `c.slot` is set: the user has that `availability` row **and** has no `pending`/`accepted` invitation on a `proposed`/`confirmed` meetup at that slot.
2. For each candidate interest row, take `sim = max over q in c.query of cosine(q.vector, row.embedding)`. Per user, keep the best `(sim, row.label, row.embedding, q.label)`.
3. Drop users with `sim < MIN_SIM`, where `MIN_SIM = 0.45` (`// tune:` calibrate with J4 seed data).
4. `score = sim * (0.8 + 0.2 * E)`, where `E = 1 / (1 + 10 ** ((1200 - reliability) / 400))`.
5. `reason` (grounded, no LLM): if the labels are equal, `"You're both into {label}"`. Otherwise, `"They're into {label}, close to your {q.label}"`.

The brute-force scan is fine to 10k users. Add a `ponytail:` comment naming `sqlite-vec` as the upgrade path.

- [ ] **Step 1: Failing tests** (hand vectors via `makeUser`)
  - Excluded: opted-out users, unconfirmed users, users unavailable at `slot`, users already holding a pending invite at `slot`, ids in `excludeUserIds`, `mode='pair'` users for `kind:'group'`, and users with `sim` below 0.45.
  - Ordering: `axis(0)` beats `blend(axis(0), axis(1), 0.5)`.
  - Equal sim → reliability 1400 ranks above 1000.
  - A query with two vectors matches a user on either one, so "philosophy + soccer" people are eligible for both groups.
  - `reason` contains both labels when they differ.
- [ ] **Step 2:** Run `npm test`. Expected: FAIL.
- [ ] **Step 3: Implement** per the algorithm.

### Task A2: `recordResponse` (state, capacity, confirmation, bias)

**Files:** Replace `src/meetups/responses.ts`; Test `test/meetups/responses.test.ts`

**Interfaces:**
- Consumes: `tx`, `sendMessage`, `mean`, `normalize`, `findCandidates`
- Produces: `recordResponse(userId, proposalId, reply, now): Promise<ResponseResult>`, `openInvitations(userId, reply): number[]`, `backfill(meetupId, now): Promise<void>`

Rules, all inside one `tx`, with messages sent after commit:
- The user has no invitation row for this meetup → `not_invited`.
- The meetup is `expired`/`cancelled`/`done`, or `now > deadline` on a `proposed` meetup → `closed`. Change nothing and reply `"That one closed. I'll find you another."`
- `yes`: if the accepted count is already `max_size` → set the invitation to `full` and reply `"It filled up, you're first in line next time."`. Otherwise set it to `accepted`, then recompute `embedding = normalize(0.5*seed_embedding + 0.5*mean(each accepted member's interest vector closest to seed_embedding))` (`EVENT_BIAS = 0.5`, `// tune:`).
  - If the count reaches `min_size` and the state is `proposed` → `confirmed`. Send everyone accepted: `"Confirmed: {activity}, {formatSlot} at {place}. Meet at {meetSpot}. Going: {first names}. CANCEL {id} if plans change."` (key `confirm:{id}:{uid}`).
  - If the meetup was already `confirmed` → send the joiner the confirmation, and send the others `"{name} is joining too."` (key `joined:{id}:{joiner}:{uid}`).
  - Otherwise → `"You're in. I'll confirm once {min − count} more say yes."`
- `pass` → `declined`, reply `"No worries."`
- `cancel` (on an accepted invitation) → `cancelled`. Tell the remaining accepted people `"{name} can't make it."` If accepted < min: when `now < slot − 2h`, set the state to `proposed` and call `backfill` (invite the next `min − count` from `findCandidates({query:[{label:activity, vector:embedding}], kind, slot, excludeUserIds: everyone already invited})`). ### Task A3: Planner (`planMeetups`)

**Files:** Create `src/meetups/planner.ts`; Test `test/meetups/planner.test.ts`

**Interfaces:**
- Consumes: `findCandidates`, `createProposal`, `upcomingSlots`, `cosine`, `mean`
- Produces: `planMeetups(now: Date): Promise<number>` (the number of proposals created)

Algorithm (greedy, run on onboarding completion and every tick):
```
busy = users with pending/accepted invites on proposed/confirmed meetups whose slot > now
for u in active, confirmed, not opted-out, not busy users, oldest first:
  slots = u.availability ∩ upcomingSlots(now)
  if u.mode in (group, both):
    for interest i of u:
      best = argmax over s in slots of findCandidates({query:[i], kind:'group', slot:s, excludeUserIds:[u, ...busy]})
      group = [u]; centroid = i.vector
      for c in best.candidates:                      // already score-sorted
        if cosine(c.vector, centroid) >= GROUP_MIN_SIM (0.5, tune): add c; centroid = mean(i.vector, members' vectors)
        stop at 6
      if group.length >= 3: createProposal(group, activity=i.label, category=i.category, vector=i.vector, slot=s, visibility='public'); busy += group; next u
  if u.mode in (pair, both) and nothing proposed for u:
    best = top candidate across slots of findCandidates({query: all of u's interests, kind:'pair', slot:s, excludeUserIds:[u, ...busy]})
    if best: createProposal(pair, activity=best.label, vector=best.vector, slot, visibility='private'); busy += both
```
Group meetups are public and pair meetups are always private.
